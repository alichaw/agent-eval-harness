# T3 scope authorization record

This file is the written record for expanding this harness's authorized scope
to include T3 (access / lateral movement), as drafted in `policy.yaml`'s
`t3_low`/`t3_high` sections (commit `fd7e40a`). It exists so that the approval
can be checked against a written record rather than relying only on a chat
transcript.

## What is being authorized

- Scope: `t3_low` and `t3_high` tool tiers exactly as written in `policy.yaml`
  at commit `fd7e40a`.
- Summary for a non-technical reader:
  - T3-Low permits controlled SSH pivoting and further enumeration through the
    already-authorized Windows Server 2025 laboratory VM.
  - T3-High permits controlled credential extraction, lateral-movement
    validation, and password-guessing against the same authorized laboratory
    asset.
  - The complete tool list and execution requirements are defined in
    `policy.yaml`.
- Assets in scope:
  - `asset:winsrv2025-01` only
- Assets explicitly OUT of scope:
  - Corporate networks, systems, VPNs, and company-managed endpoints
  - Production, staging, development, and shared enterprise systems
  - The operator's Windows and WSL hosts, except as the approved harness
    execution platform
  - Any other AWS EC2 instance, VPC resource, subnet, account, or cloud service
  - AWS instance metadata and link-local endpoints, including
    `169.254.169.254`
  - Domain controllers, identity providers, IAM systems, and shared directory
    services outside `asset:winsrv2025-01`
  - Internet hosts and third-party systems
  - Any destination reached through pivoting that is not explicitly listed in
    the asset allowlist
  - Any newly discovered hostname, IP address, account, service, or network
    route that has not been separately authorized

Because only `asset:winsrv2025-01` is currently authorized, lateral-movement
testing is limited to validating harness controls and expected blocking
behavior. Actual movement to another host requires separate authorization.

## Conditions / constraints set by the approver

No additional constraints were explicitly stated by the approver beyond the
authorized laboratory scope. The following existing project safety controls
remain mandatory:

1. All T3 activity must be limited to `asset:winsrv2025-01`.
2. Exact target allowlist enforcement must remain enabled.
3. T3 actions must not reach corporate networks, Internet hosts, other AWS
   resources, or any unlisted asset.
4. T3-High actions require a short-lived, single-use approval token bound to
   the exact asset, profile, parameters, run, and expiration time.
5. Only laboratory accounts and credentials may be used, collected, or tested.
6. Credentials must be redacted from normal output, excluded from source
   control, and deleted or rotated after testing.
7. Password guessing must use an approved account list, bounded password list,
   rate limit, attempt limit, timeout, and account-lockout safeguards.
8. Persistence, destructive actions, denial-of-service, security-control
   disabling, and log deletion are prohibited.
9. Every action must produce a complete trace and final policy verdict.
10. Fail-closed behavior, timeout enforcement, kill switch, credential
    redaction, and approval-token anti-replay controls must remain active.
11. A VM snapshot or equivalent recovery point must be created before
    T3-High testing.
12. Testing must stop immediately if:
    - the resolved target differs from the authorized asset;
    - an unexpected asset or route becomes reachable;
    - real corporate or personal credentials are encountered;
    - isolation, logging, approval validation, or the kill switch fails;
    - unintended operational impact is detected.
13. Changes to the tool list, target scope, network topology,
    credential-handling rules, or approval model require review and
    reauthorization.
